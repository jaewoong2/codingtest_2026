# [프로그래머스 388353] 지게차와 크레인 풀이 첨삭

## 총평

- **판정**: 정답
- **핵심 이유**: 창고 바깥에 빈칸 테두리를 추가하고, 지게차 요청마다 `(0, 0)`에서 외부와 연결된 빈칸을 BFS로 탐색합니다. 탐색 중 처음 만난 목표 컨테이너만 제거 대상으로 기록하고 그 너머로 진행하지 않으므로, 요청이 들어온 순간 접근 가능한 컨테이너를 정확히 골라냅니다. 크레인 요청도 종류가 같은 모든 좌표를 제거합니다.

## 문제 핵심

- `storage`는 최대 `50 × 50` 크기의 컨테이너 격자입니다.
- 길이 1인 요청은 지게차 요청입니다. 요청 시점에 창고 외부와 상하좌우로 연결된 해당 종류의 컨테이너만 모두 꺼냅니다.
- 길이 2인 요청은 크레인 요청입니다. 접근 가능 여부와 관계없이 해당 종류의 컨테이너를 모두 꺼냅니다.
- 요청은 최대 100개이며, 모든 요청 처리 후 남은 컨테이너 수를 반환해야 합니다.

지게차의 “접근 가능”은 단순히 원래 격자의 가장자리에 있는지를 뜻하지 않습니다. 이전 요청으로 생긴 빈칸을 따라 외부에서 도달할 수 있는지도 포함합니다. 또한 한 요청에서 컨테이너를 제거해 새로 열린 길은 다음 요청부터 사용할 수 있습니다.

## 현재 접근법

1. `extend()`로 원래 창고 둘레에 값 `0`인 빈칸 테두리를 한 겹 추가합니다.
2. `keys`에 요청된 종류별 컨테이너 좌표를 저장합니다.
3. 지게차 요청이면 `search_from_outside()`를 호출합니다.
   - 테두리의 `(0, 0)`에서 BFS를 시작합니다.
   - 외부와 연결된 `0`은 계속 탐색합니다.
   - 목표 종류를 만나면 제거 목록에 넣되, 그 칸 너머로는 탐색하지 않습니다.
   - BFS가 끝난 후 제거 대상을 한꺼번에 `0`으로 바꿉니다.
4. 크레인 요청이면 `keys`에 저장된 해당 종류의 모든 좌표를 `0`으로 바꿉니다.
5. 최종 격자에서 `0`이 아닌 칸의 수를 반환합니다.

바깥 테두리를 추가한 덕분에 원래 격자의 네 변을 각각 시작점으로 관리하지 않고 `(0, 0)` 한 곳에서 외부 공간 전체를 탐색할 수 있습니다. 좋은 모델링입니다.

## 정확성 및 반례

반례를 발견하지 못했습니다.

### 지게차 요청이 정확한 이유

- 추가한 0 테두리는 실제 창고 외부를 나타냅니다.
- BFS는 `(0, 0)`에서 시작해 0인 칸만 통과하므로, 방문한 0은 모두 현재 외부와 연결된 빈 공간입니다.
- 그 공간과 상하좌우로 맞닿은 목표 컨테이너는 지게차가 접근할 수 있으므로 제거 목록에 포함됩니다.
- 목표 컨테이너를 발견했을 때 `continue`하여 그 너머를 탐색하지 않습니다. 따라서 그 컨테이너가 아직 놓여 있는 요청 시작 시점에는 접근할 수 없던 내부 공간까지 잘못 탐색하지 않습니다.
- 모든 제거 대상을 `search()` 종료 후 한꺼번에 0으로 바꾸므로, 같은 요청에서 새로 노출된 목표 컨테이너가 연쇄 제거되지 않습니다.

예를 들어 다음 입력에서는 바깥쪽 A 8개만 제거되고 중앙 A는 남아야 합니다.

```python
storage = ["AAA", "AAA", "AAA"]
requests = ["A"]
```

현재 코드의 **실제 출력은 `1`**로 기대값과 일치했습니다. 요청을 한 번 더 수행한 `requests = ["A", "A"]`에서는 중앙 A가 다음 요청에 접근 가능해져 실제 출력이 `0`이었습니다.

### 크레인 요청이 정확한 이유

`keys`에는 해당 종류가 처음 놓였던 모든 좌표가 들어 있습니다. 이전 요청으로 이미 제거된 좌표를 다시 0으로 바꾸더라도 상태와 개수에는 영향이 없고, 아직 남은 해당 종류는 모두 제거됩니다. 한 번 크레인으로 제거한 종류의 목록을 비우는 것도 이후 같은 크레인 요청에서 할 일이 없다는 사실과 맞습니다.

따라서 지게차와 크레인 모두 문제의 제거 규칙을 만족합니다.

## 복잡도

`N`, `M`을 원래 격자의 행과 열, `R`을 요청 수라고 하겠습니다. 최댓값은 `N, M <= 50`, `R <= 100`입니다.

- `extend()`는 모든 칸을 복사하므로 `O(NM)`입니다.
- `keys` 생성은 요청마다 확장된 격자 전체를 순회하므로 `O(RNM)`입니다.
- 지게차 요청 한 번의 BFS는 각 칸을 최대 한 번 방문하므로 `O(NM)`입니다. 지게차 요청이 최대 `R`번이므로 총 `O(RNM)`입니다.
- 크레인 좌표 처리도 `keys`에 저장된 좌표 수에 비례하며, 현재 중복 저장 방식까지 고려하면 전체 최악 비용은 `O(RNM)`입니다.
- 마지막 남은 컨테이너 계산은 `O(NM)`입니다.

따라서 전체 **시간 복잡도는 `O(RNM)`**입니다. 최대 규모는 대략 100번에 걸쳐 2,500칸을 탐색하는 수준이어서 충분합니다.

공간은 확장 격자와 BFS의 `visited`, `queue`, `arr`에 각각 `O(NM)`이 필요합니다. 다만 현재 `keys`는 같은 종류가 요청에 반복 등장할 때 동일 좌표를 반복 저장하므로 최악에는 **`O(RNM)`**까지 사용할 수 있습니다. 최대 입력에서는 통과 가능한 규모지만 줄일 수 있습니다.

## 필수 수정

없습니다.

## 선택적 개선

### 1. `keys`의 중복 좌표 저장 제거

현재는 다음 구조로 요청마다 격자 전체를 다시 훑습니다.

```python
for request in requests:
    for i in range(len(storage)):
        for j in range(len(storage[i])):
            if request[0] == storage[i][j]:
                keys[request[0]].append((i, j))
```

예를 들어 `"A"` 요청이 100번 등장하면 모든 A 좌표가 같은 리스트에 100번씩 저장됩니다. 정답에는 영향을 주지 않지만 전처리 시간과 공간이 커집니다. 격자를 한 번만 순회하며 문자별 좌표를 저장하면 `O(NM)` 시간과 공간으로 줄일 수 있습니다.

```python
from collections import defaultdict

positions = defaultdict(list)
for i in range(len(storage)):
    for j in range(len(storage[i])):
        if storage[i][j] != 0:
            positions[storage[i][j]].append((i, j))
```

### 2. 크레인 목록은 반복문이 끝난 뒤 비우기

현재 `keys[request[0]] = []`가 좌표 반복문 안에 있습니다.

```python
for r, c in keys[request[0]]:
    storage[r][c] = 0
    keys[request[0]] = []
```

파이썬의 `for` 반복자는 기존 리스트를 계속 참조하므로 현재 코드도 모든 좌표를 정상 처리합니다. 하지만 목록을 첫 좌표 처리 중에 비우는 것처럼 보여 의도를 오해하기 쉽습니다. 반복문 이후로 옮기는 편이 명확합니다.

```python
for r, c in keys[request[0]]:
    storage[r][c] = 0
keys[request[0]] = []
```

### 3. 두 요청 분기는 `if` / `else`로 표현하기

요청 길이는 1 또는 2로 서로 배타적이므로 두 번째 `if`를 `else`로 쓰면 둘 중 정확히 한 동작만 수행한다는 의도가 더 분명합니다. 이는 가독성 개선이며 정답 여부에는 영향이 없습니다.

### 4. `visited`를 함수 안에서 만들기

`visited`는 항상 `search_from_outside()`가 생성해 `search()`로 넘깁니다. 두 함수가 하나의 BFS 동작을 나누고 있으므로, 필요하다면 `search()` 안에서 생성하고 제거까지 한 함수에 모아 흐름을 단순화할 수 있습니다. 현재 함수 분리도 동작상 문제는 없습니다.

## 실행 검증

- 공식 예제 1: 실제 출력 `11`, 기대값 `11`
- 공식 예제 2: 실제 출력 `4`, 기대값 `4`
- `3 × 3` 전체가 A이고 지게차 A 요청 1회: 실제 출력 `1`
- 같은 입력에 지게차 A 요청 2회: 실제 출력 `0`
- 요청한 종류가 없는 크레인 요청: 정상적으로 기존 컨테이너 수 유지
- 작은 무작위 격자와 요청 3,000건을 독립 기준 풀이와 교차 검증: 모두 일치
- `50 × 50` 전체가 A이고 크레인 A 요청 100회: 실제 출력 `0`
- `50 × 50` 전체가 A이고 지게차 A 요청 100회: 실제 출력 `0`

실행 테스트는 보조 근거이며, 정답 판정은 외부와 연결된 빈 공간만 탐색하고 목표 컨테이너에서는 탐색을 멈춘다는 BFS의 성질로 확정했습니다.

## 이 문제에서 읽어야 할 신호

- **“4면 중 적어도 1면이 창고 외부와 연결”** → 외부에서 빈 공간을 따라 도달 가능한지 확인하는 격자 탐색
- **“요청이 들어온 순간 접근 가능한”** → 제거 대상을 먼저 확정하고 이후에 상태를 갱신
- **길이 1과 길이 2인 요청** → 지게차와 크레인의 제거 규칙 분기
- **요청이 순서대로 주어짐** → 이전 요청으로 생긴 통로가 다음 요청의 접근 가능성에 영향
- **`N, M <= 50`, 요청 100개** → 요청마다 격자 전체를 BFS해도 가능한 연산 규모

## 다음 문제를 위한 체크포인트

- 외부를 0 테두리로 확장해 하나의 BFS 시작점으로 만든 모델링이 좋습니다.
- 목표 컨테이너를 만난 시점에 탐색을 멈추고 BFS가 끝난 뒤 일괄 제거한 점이 이 문제의 가장 까다로운 조건을 정확히 처리합니다.
- 다음에는 좌표 전처리를 할 때 요청을 기준으로 격자를 반복 탐색하기보다, 격자를 한 번 읽으며 종류별로 분류할 수 있는지도 확인해 보세요.
