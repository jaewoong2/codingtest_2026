## 총평

- 판정: **오답 (시간 초과 가능)**
- 핵심 이유: 실패율 계산 논리는 맞지만, 각 사용자가 도달한 이전 스테이지를 모두 순회합니다. 최악의 경우 약 `200,000 × 500 = 100,000,000`회의 딕셔너리 갱신이 발생합니다.

## 문제 핵심

스테이지 `i`의 실패율은 `i`에 도전 중인 사람 수 ÷ `i`에 도달한 사람 수입니다. 각 사용자의 현재 스테이지만 세면 되고, 이전 스테이지들을 사용자마다 다시 세지 않아도 됩니다.

## 현재 접근법

`n_pass`에는 통과 인원, `n_pass_with_challenge`에는 도전 또는 통과 인원을 저장한 뒤 성공률을 오름차순 정렬하고 있습니다. 성공률 오름차순은 실패율 내림차순과 같고, 같은 비율에서는 입력 순서가 스테이지 번호 오름차순이므로 정렬 기준도 정확합니다.

## 정확성

두 공식 예제를 직접 실행했습니다.

- `solution(5, [2, 1, 2, 6, 2, 4, 3, 3])` → `[3, 4, 2, 1, 5]`
- `solution(4, [4, 4, 4, 4, 4])` → `[4, 1, 2, 3]`

둘 다 기대값과 일치합니다. `stage == N + 1`인 사람도 모든 `1..N` 스테이지를 통과한 것으로 세기 때문에 논리상 처리도 맞습니다.

## 복잡도

- `S`: 사용자 수, `N`: 스테이지 수
- 현재 코드: 각 사용자가 `stage - 1`개의 이전 스테이지를 순회하므로 `O(SN)` 시간, 딕셔너리 두 개와 정렬 결과로 `O(N)` 공간입니다. `S=200,000`, `N=500`이면 최악 약 1억 번 갱신입니다.
- 권장 방식: 현재 스테이지별 인원만 한 번 세고, 남은 도전자 수를 앞에서부터 빼 가면 `O(S + N log N)` 시간, `O(N)` 공간입니다.

## 필수 수정

각 사용자의 현재 스테이지 빈도만 `count[stage]`에 기록하세요. 처음 도전자 수를 `len(stages)`로 두고, 스테이지 `i`에서 `count[i] / 남은_도전자`를 계산한 뒤 `남은_도전자 -= count[i]`로 갱신하면 됩니다.

### 예제 코드

```python
def solution(n, stages):
    count = [0] * (n + 2)

    # 각 사용자가 현재 도전 중인 스테이지만 센다.
    for stage in stages:
        count[stage] += 1

    remaining = len(stages)
    failure_rates = []

    for stage in range(1, n + 1):
        if remaining == 0:
            failure_rate = 0
        else:
            failure_rate = count[stage] / remaining

        failure_rates.append((failure_rate, stage))
        remaining -= count[stage]

    # 실패율 내림차순, 같으면 스테이지 번호 오름차순
    failure_rates.sort(key=lambda x: (-x[0], x[1]))
    return [stage for _, stage in failure_rates]
```

`count[stage]`는 그 스테이지에서 멈춘 사람 수이고, `remaining`은 해당 스테이지에 도달한 사람 수입니다. 현재 스테이지의 인원을 뺀 뒤 다음 스테이지로 넘어가므로 분모를 중복 계산하지 않습니다.

## 선택적 개선

- 실패율을 직접 저장하면 `성공률 오름차순`으로 바꾸어 생각할 필요가 없어 코드 의도가 더 선명해집니다.
- 스테이지 번호가 연속된 작은 정수이므로 딕셔너리보다 길이 `N + 2` 리스트가 더 단순하고 빠릅니다.

## 이 문제에서 읽어야 할 신호

각 사용자의 상태가 “현재 멈춘 스테이지” 하나로 주어지고, 스테이지를 앞에서부터 처리할 수 있습니다. 이때는 누적 정보를 사용자별로 펼치기보다 **빈도 수 + 누적 감소**로 집계할 수 있는지 확인하세요.
